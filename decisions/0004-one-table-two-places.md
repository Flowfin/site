# 0004. One table in two places

The organisation profile publishes a table of the plugins and the state each one
is in. The site will say the same thing. Two hand-maintained copies of one table
disagree eventually, and the disagreement is invisible until a reader finds it,
which is the worst way for it to be found. One of the two has to be derived from
the other.

## What was measured

The profile table as published:

    gh api repos/Flowfin/.github/contents/profile/README.md --jq '.content' \
      | base64 -d | grep -c '^| \['
    12

Run 2026-08-09. Twelve rows of Markdown inside a README, edited by hand, in a
different repository from this one.

## The decision

Both the site and the profile table are derived from the roster. The direction
of generation runs from the roster to the profile table, and never from the
profile table to anything.

The build renders the table out of the roster into the exact shape the profile
expects. A check compares what it rendered against what the profile currently
publishes, reports the difference, and stops there. It reads across the
repository boundary and it does not write. Nothing here writes into that
repository.

## Why

The profile table is the least machine-readable of the three places the list
appears and the hardest to check. Deriving the roster from it would mean parsing
prose that a person edits freely, and the first cell somebody reflows breaks the
parse. The parse failing loudly would be the good day; the parse succeeding on a
reflowed cell and producing a wrong state word is the ordinary one.

Emitting Markdown is the easy direction. A table is a shape a generator can hit
exactly, and comparing generated bytes against published bytes is a string
comparison rather than a parse. That turns a silent disagreement into a red
check, which is the whole point of choosing a direction at all.

The check reports rather than writes because the profile is not this
repository's to change. A job that edited another tree would need a credential
that reaches it, and it would repair the symptom in the place a reader looks
while leaving whoever edited by hand with no idea they had been overridden.
Reporting leaves the fix with the person who caused it.

## What the alternatives cost

Derive the roster from the profile table. The cost is the parsing above: prose
as an input format, a break on the first reflow, and a wrong answer rather than
an error in the cases that do not break. It also puts the machine-readable
source inside a document written for people.

Keep both by hand and rely on review to hold them equal. The cost is drift found
by a reader rather than by a check, which is the failure this record exists to
remove, and it is the same failure record 0007 refuses for the design tokens.

Have this build write the profile table directly. The cost is a credential that
reaches another repository, held by a job here, plus commits landing in that
tree from a source its own maintainer is not reading.

## When this is worth revisiting

The profile table gaining a column the roster cannot answer, which would make
the profile a source of something rather than a rendering of the roster, and
would turn this into a question about that column.
